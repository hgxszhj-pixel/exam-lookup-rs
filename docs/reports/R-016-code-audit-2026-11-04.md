## P0-1 真实数据上整个 load 失败（一个坏文件 → 零产出）

**现象**（实跑）：

```
$ exam-cli --data-root ~/x_videos-dowloads/exam-lookup index --out /tmp/q.db
Error: json parse error at .../banks/web-learned.json:
  invalid type: string "30分钟", expected a sequence at line 35 column 27
```

**根因链**：

1. `crates/exam-engine/src/types.rs:155-156` —— `answer_text: Vec<String>`。
   `#[serde(default)]` 只在**字段缺失**时生效，**不处理类型不符**。
2. 真实数据 `banks/web-learned.json` 里 7 道题的 `answerText` 是**标量字符串**（`"30分钟"`、`"20kg"`、`"三级"`…）。
3. Python 端**显式兼容**这种形态 —— `kb_db.py:628-631`：
   ```python
   items = at if isinstance(at, list) else ([at] if at else [])
   ```
   → 这是**移植时丢失的契约**，不是坏数据。
4. `crates/exam-engine/src/source/json_banks.rs:145` 用 `?` 直接向上传播：
   ```rust
   let result = load_one_bank(&path, BankId(stem))?;
   ```
   **没有 per-file 隔离**，一个文件解析失败 → 整个 `load()` 中止。
5. `crates/exam-engine/src/index.rs:171` `source.load(data_root)?` 继续传播 → 整个 rebuild 归零。

**实测影响**：真实 data_root 下 `banks/` 有 17 个合法题库（共 1768 题），
Rust 端能加载的只有 16 个（1761 题），第 17 个（7 题）直接把**全部 16 个也一起拖垮** —— 实际产出 0 个题库。
Python 侧 `dump_banks.py` 对同一目录输出 **1768 题，0 错误**。

**影响面**：`exam-cli index` / `exam-cli dump` / `exam-cli load`（全量）/ GUI 的 "Rebuild now" / watcher 自动重建 —— **全部不可用**。
GUI 侧是优雅失败（`state.rs:268` 把错误转成字符串回传 UI），不会崩，但功能等于没有。

**修复方向**：

- (a) 给 `answerText`（及 `answerKeys`）加宽容反序列化：`#[serde(deserialize_with = "string_or_vec")]`，标量 → 单元素数组。
  与 Python `_blank_answers` 行为对齐。
- (b) `load_one_bank` 改为 per-file 隔离：单文件失败记入 `BuildStats.errors` 并 continue，**不要**中止整体。
  `BuildStats.errors` 现在只统计行级 SQLite 失败，**从不统计文件级解析错误** —— 这正是"0 错误"假象的来源。
- (c) 校验题库文件的 `schema_version`（Python 强制 `== 1`，Rust 侧**完全不读**该字段）。

## P0-2 parity 门禁恒真 —— R-015 的 "0.00% diff" 是除零假象

`scripts/dump_parity.sh:61-62` 用 **`wc -l` 统计 JSON 文件的行数**做分母：

```bash
TOTAL_PY_LINES=$(wc -l < "$NORM_PY")
TOTAL_RUST_LINES=$(wc -l < "$NORM_RUST")
```

但第 50 行的 `json.dump(out, open(p,"w"), ...)` **不带 indent、不写尾随换行** → 输出是**单行** → `wc -l` = **0**。

于是 `DENOM=0` → 走 `dump_parity.sh:64-66` 的 `PCT="0.00"` 分支 → `dump_parity.sh:71` 的门禁 `p<=1.0` **恒真** → 永远输出 `✅ parity OK`。

**实跑验证**：两个**完全不同**的 dump 比对，结果仍是 `diff lines: 6 / ~0 (0.00%) ✅ parity OK`，exit 0。

叠加 P0-1：脚本现在其实**连跑都跑不完** —— 第 [2/4] 步 Rust dump 撞上同一个 `web-learned.json` 解析错误就退出。

**结论**：R-015 的 "1760 Q 0.00% diff" **不是测量结果，是除零产物**。
整个 parity 验收链（`dump_banks.py` → `dump_parity.sh` → R-015 报表）当前**无鉴别力**。

**修复方向**：分母改成**题目条数**（`len(questions)`）而非文件行数；差异率按题目维度算。
另：`dump_parity.sh:20` 写死共享 `/tmp/exam-parity`（并行任务互相覆盖）、`dump_parity.sh:37-56` 的 heredoc 未加引号（路径含空格即崩）、
`dump_parity.sh:19` 硬编码 `/Users/hgxszhj/x_videos-dowloads/exam-lookup`（换机即废）。

## P1-1 FTS join 扇出 —— 检索结果一半是重复

**现象**（实跑，索引 21 bank / 1761 题 / 1278 cards）：

```
$ exam-cli search --db q.db "有限空间" --limit 16 --json
returned rows: 16   distinct ids: 8
duplicated: ['DTZX-m0045','DTZX-s0033','DTZX-m0056','DTZX-s0035',
             'TXAQ-s0004','TXAQ-s0007','DTZX-s0037','DTZX-j0027']
```

**根因**（实测表行数）：

| 表 | 行数 | 说明 |
|---|---|---|
| `q` | **1632** | `id TEXT PRIMARY KEY` + `INSERT OR REPLACE` → 跨 bank 同 id 被去重 |
| `q_fts` | **1761** | `index.rs:267` 普通 `INSERT` → **无去重** |
| `q_fts` distinct id | 1632 | 同上 |
| `card` | 1048 | 同病 |
| `card_fts` | **1278** | 同病 |

129 个问题 id 跨 bank 重复（`DTZX-*` 62 个、`TXAQ-*` 50 个等）。
`search.rs:160-163` 的 `q_fts JOIN q ON q.id = q_fts.id` 于是**一对多扇出**，同一条命中重复返回。

**次生影响**：`LIMIT` 作用在 join 之后的行上 → **limit=16 实际只给出 8 个不同问题**，
用户永远只看到一半的结果，且 `bm25` 排序被重复行干扰。

**另一条独立触发路径**：`IndexBuilder::populate` 是 **public**，注释写明"不清空,增量插入"（`index.rs:160`），
但 `q_fts` 用普通 `INSERT` 而 `q` 用 `INSERT OR REPLACE` → **同一个库调两次 populate 也会产生重复**。
两个根因指向同一处修复。

**修复方向**：让 `q_fts` 由 `q` 派生而非平行维护 —— 改用 external-content FTS5
（`content='q', content_rowid='rowid'`）+ trigger，或插入前 `WHERE id NOT IN (SELECT id FROM q_fts)` 去重。
同时 `index.rs:7` 的注释声称 `q_fts` 是 `content='q'`，**与实现不符**。

## P1-2 LIKE 转义完全失效 —— 兜底路径对含 `%` `_` `\` 的查询永不命中

`search.rs:403-407`：

```rust
fn escape_like(s: &str) -> String {
    // SQLite LIKE 默认 escape 关闭;转义 `%` `_` `\`
    s.replace('\\', "\\\\").replace('%', "\\%").replace('_', "\\_")
}
```

注释自己写明 "SQLite LIKE 默认 escape 关闭"，**却仍然输出反斜杠转义**。
而 `search.rs:190` / `search.rs:272` 的两条 LIKE 查询**都没有 `ESCAPE '\'` 子句**。

SQLite 在无 ESCAPE 时把 `\` 当**普通字面量**，于是模式 `%a\%b\_c%` 永远匹配不到字面值 `a%b_c`。

**测试为什么是绿的**：`search.rs:503` 的 `escape_like_handles_wildcards` **只断言转义后的字符串**
（`assert_eq!(escape_like("a%b_c"), "a\\%b\\_c")`），**从不验证 SQL 是否匹配**。
整个转义机制坏掉，测试照绿 —— 正好违反本仓"改 1–2 行期望行为必须让测试变红"的约定。

**旁证**：`search.rs:447` 的 `like_fallback_for_substring` 号称测 LIKE 兜底，
但 FTS 已能命中，即使**整个删掉 `try_like`** 该测试照样通过 —— 它从没钉住兜底路径。

### P2-1 三态缓存目前是装饰性的
`compute_status` 的过期算术本身正确，但**只在写入时被调用**（`scheduler.rs:168`，`now` vs `now` → 恒为 `Fresh`）。
`CacheStore::get` / `list`（`cache.rs:210`、`cache.rs:238`）**原样读取存储的 `status` 列**

### P2-2 调度用 wall-clock，时钟跳变即错乱
`scheduler.rs:255` 用 wall-clock `now_secs()` 而非 `Instant`。
时钟前跳 → 所有 source 同时到期（惊群）；时钟后跳 → `now - last_run` 为负、age 钳到 0
→ 在时钟追上之前**永不触发**。`run_loop_for` 用 `Instant` 算自身时长、用 wall-clock 算调度 —— 一个循环两套时钟。

### P2-3 无 DB 迁移路径
`index.rs:21,115` 的 `SCHEMA_VERSION = 2` 存在 `meta` 表，且 `init_schema` **每次无条件覆写**。
全仓 `user_version` 零命中（只有 `journal_mode`）。所有 DDL 是 `CREATE TABLE IF NOT EXISTS`
→ 将来加字段时代码有、**存量库没有**，且没有任何升级手段。修 P1-1 若要改 FTS schema，**必须先补迁移机制**。

### P2-4 `rebuild()` 是三个独立事务
`index.rs:145-147`：`init_schema → truncate → populate` 各自提交。
truncate 与 populate 之间，并发读连接（`state.rs:271` 保留旧只读连接）看到**空索引**；
populate 失败则磁盘索引被摧毁且**不恢复**。叠加 `index.rs:99,125,168,354` 的 `unchecked_transaction`。

## 环境问题：`rtk --ultra-compact` 让所有被改写命令静默返回 0

用户 shell 里有 `alias rtk='rtk --ultra-compact'`，而该模式下**任何命令**都返回：

```
[rtk: No such file or directory (os error 2)]
```

且 **exit code = 0**。由于 Claude Code 的 hook 会把 `cargo test` / `git status` / `ls` 等改写成 `rtk <cmd>`，
这些命令会**输出空 + 返回 0** —— 典型假绿灯。

**本次审计中首次 `cargo test --workspace` 就是这样"通过"的（无任何输出，rc=0）。**
绕过办法：命令前缀 `command `（`command cargo test`），或直接用 `/usr/local/bin/rtk`（不带 alias 展开）。

> 建议：修 `rtk` 的 `--ultra-compact` 实现，或摘掉该 alias —— 否则任何依赖退出码的自动化都会失效。

## 追加：GUI 手工烟测记录（2026-11-04）

P1-3 / P1-4 是**只有真机能验**的两条 —— 自动化测试覆盖不到线程调度与渲染时序。
本节记录一次可复现的手工烟测，作为「建议修复顺序」表里 GUI 侧的验收证据。

### 环境

- 语料：合成语料 **121 题库 / 240,000 题 / 120,000 卡片**（141 MB）。
  真实语料只有 1,768 题，重建不到 1 秒 —— **"重建中…" 根本来不及渲染**，必须放大语料才测得出。
- 驱动方式：macOS AX（`cua-computer-use`）后台点击 + 截图，不抢前台。
- 被测二进制：`target/release/exam-app`。

### 三条断言

| 断言 | 怎么测的 | 结果 |
|---|---|---|
| 手动重建时按钮显示"重建中…" | 点「重建索引」，在 24 万题的重建进行中截图 | ✅ 按钮文案变成"重建中…"且置灰禁用，状态段同步显示"重建中…" |

| watcher 启停不卡 UI | 重建**进行中**关掉 watcher 开关 | ✅ 见下方时间线 |

### watcher 启停的时间线（关键证据）

关 watcher 那条路径会 `stop_watcher()` → `join()` 消费线程；若消费线程正在重建，
`join()` 会**阻塞到重建结束**。所以要证明"不卡 UI"，必须**在重建进行中**去关开关，
并验证 UI 线程没有跟着等。

| 时刻 | 事件 | 来源 |
|---|---|---|
| 23:08:32.581 | watcher 消费线程启动 | app 日志 |
| 23:08:54 | `touch` 语料文件 → 触发重建（跑了 33 秒） | 操作记录 |
| ~23:08:57 | 点关 watcher → **UI 立刻**重绘成"未启用 — 需手动点「重建索引」"；同一帧设置页显示 **"DB 未加载"**（= 重建进行中的标记） | 截图 |
| 23:09:27.162 | 重建完成 | app 日志 |
| 23:09:27.184 | 消费线程退出（`join()` 在重建结束后 22 ms 返回） | app 日志 |

UI 在 23:08:57 就已经响应了，而消费线程直到 23:09:27 才真正退出 —— **中间隔了 30 秒**。
即 `join()` 阻塞的是**后台线程**，UI 线程全程未被阻塞。
