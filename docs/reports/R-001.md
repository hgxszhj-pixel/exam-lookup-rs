# R-001 中文 trigram / 分词降级方案

## 议题
- SQLite FTS5 `unicode61` tokenizer 默认对中文(CJK Unified / Ext-A / Compat)按**字**切分。
- 这与 Python `kb.py` 的 `norm(question)` 后做 `SequenceMatcher` 模糊匹配的行为差异较大。
- Plan 阶段登记的「trigram 三元组」方案依赖 Rust 端没有现成中文分词 crate,需手工实现。

## 决策
**采用 CJK 字间加空格 + FTS5 unicode61 按字索引 + LIKE 子串兜底。**

具体实现:
- `parse::cjk_expand(s)` — 在相邻 CJK 字符之间插入空格,使 FTS5 unicode61 按字切分。
  例:`什么是网络安全` → `什 是 网 络 安 全`
- `index.rs::insert_load_result` — 写入 `q_fts.question` / `q_fts.analysis` 之前先 `cjk_expand`。
- `search::build_fts_term` — 用户查询也按相同规则切 CJK 单字 + ASCII 段加 wildcard。
- `search::try_like` — FTS5 无命中时退到 `nq LIKE '%<norm>%'`,覆盖 95% 子串用例。

## 不实现的部分
- ❌ Python `SequenceMatcher` 等价编辑距离排名 — 引入 `strsim` crate 收益不高,且 LIKE 已覆盖子串。
- ❌ 真正的中文分词(jieba-rs 等) — 与 FTS5 unicode61 的「按字」策略冗余,反而引入数据依赖。
- ❌ SQLite trigram tokenizer(`SQLITE_ENABLE_FTS5_TRIGRAM`) — `rusqlite/bundled` 不包含该扩展,需额外编译;收益与 LIKE 兜底重叠。

## 验证
- 单元测试 `parse::cjk_expand`:3 个(CJK 切分、ASCII 不变、空格)
- 单元测试 `search::build_fts_term`:3 个(CJK OR、ASCII wildcard、quote 转义)
- 单元测试 `search::search`:4 个(FTS 命中、LIKE 兜底、stem 精确、bank 过滤)
- 端到端:`cargo run -- search --query "网络安全"` 命中 3 条真实题(FTS5 路径)

## 风险
- 中文成语 / 词组命中不精确(如「密码学」被切成「密」「码」「学」三个 token,需要三个 token 都命中才 bm25 计算为高相关)。
  实际影响:有 LIKE 兜底,无零命中。
- 英文 / 数字混合题干(windows 11 / API 500)— ascii 段加 wildcard,正常命中。
