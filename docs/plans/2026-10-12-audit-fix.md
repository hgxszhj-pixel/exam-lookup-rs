### ✅ Step 1.3: JSON 文件 size cap (security MEDIUM) — DONE

**实际改动**:
- `source/mod.rs`: 新增 `pub const MAX_JSON_BYTES: u64 = 64 * 1024 * 1024` (64 MiB)
- `source/mod.rs`: 新增 helper `pub fn load_json_bounded(path, max_bytes) -> Result<Vec<u8>>` — 先 `fs::metadata().len()` 拒超 cap,再 `fs::read`
- `json_banks.rs::load_one_bank` + `crawl_cards.rs::load_one_card_file`: 替裸 `std::fs::read` 为 `load_json_bounded(..., MAX_JSON_BYTES)`

**为什么 `> max_bytes` 而不是 `>=`**:metadata.len() 返回 file 大小;`==` 不应误伤正常等大文件。

### Step 1.3: JSON 文件 size cap (security MEDIUM)

**背景**: `std::fs::read(path)` 无大小判断 → 4GB banks file OOM。

**Verify**: `Read crates/exam-engine/src/source/json_banks.rs:155-160` 和 `crawl_cards.rs:140-150`

**Fix**:
- 新增 `crates/exam-engine/src/source/mod.rs` (或 `parse.rs`) 辅助:`fn load_json_bounded(path: &Path, max_bytes: u64) -> Result<serde_json::Value>` — 先 `fs::metadata(path)?.len()`,> cap 直接 `EngineError::Other("file too large")`
- `json_banks.rs::load` / `crawl_cards.rs::load_one_card_file` 改用此 helper
- 常量 `MAX_JSON_BYTES: u64 = 64 * 1024 * 1024` (64MB 单文件上限)
- 加 test: 写一个 65MB 临时 JSON → 收到 size error

### ✅ Step 1.4: `--data-root` canonicalize (security MEDIUM) — DONE

**实际改动**:
- `source/mod.rs`: 新增 `pub fn canonicalize_path(path: &Path) -> Result<PathBuf, EngineError>` — 包装 `std::fs::canonicalize` + `EngineError::io`
- `cli/main.rs`: 抽出 `fn resolve_data_root(opt, sub) -> Result<PathBuf>` 收敛 5 处 `ok_or_else(...)`;每个 subcommand 进入前 canonicalize
- 2 个新 test: `canonicalize_path_resolves_relative` / `canonicalize_path_rejects_missing`

**macOS 兼容**:`std::fs::canonicalize` 已处理 `/var` ↔ `/private/var`(smoke test:`/tmp` → `/private/tmp`),不需要 `dunce` 包装(那是反向 un-canonicalize 用)。

**smoke 验证**:
- `cargo run -- load --source json_banks --data-root /tmp/nonexistent_xxx` → 立即报 `io error at /tmp/nonexistent_xxx: No such file or directory`
- `cargo run -- load --source json_banks --data-root /tmp/.` → 报 `schema invalid at /private/tmp/banks: ...`(macOS 解析 `/tmp` → `/private/tmp`,engine 正确指出缺 `banks/` 子目录)

**Regression**:
- `cargo build --workspace` → 0 errors
- `cargo test --workspace` → **100 passed**
- `cargo clippy --workspace -- -D warnings` → 0 errors

**Verify**: `Read scheduler.rs:124-205` — 当前 `tick` 对失败 source 写 cache 记 notes 但**没有 backoff 倍增逻辑**。`CacheEntry` 也没有 `attempts` / `next_retry_at` 字段。

**结论**:backoff 是未实现 feature,不是已实现但无测试。写一个 backoff test 必失败,等于加 TDD 红 → 后续要实现 backoff 才走这个 step。**不修**(避免 step 1.x 范围外扩张)。

### ✅ Step 3.5: IndexBuilder rebuild 边界测试 (quality-reviewer P1 #4 反馈) — DONE

**来源**:cross-session teammate `quality-reviewer` 反馈 — `IndexBuilder::rebuild` 缺空 dir + duplicate-id 覆盖。

**实际改动** (`crates/exam-engine/src/index.rs` 测试模块):
- `rebuild_succeeds_on_empty_subdirs` — banks/ + crawl/ 都存在但空 → stats 全 0,errors=0
- `rebuild_fails_fast_when_subdir_missing` — data_root 完全空 → rebuild 返回 `EngineError::Schema`(**暴露 fail-fast 语义**)
- `rebuild_handles_duplicate_ids_in_same_json` — JSON 内同 id 2 次 → `b.stats().questions == 1`(INSERT OR REPLACE 生效),`stats.questions == 2`(输入计数)

**测试驱动发现的两个契约**(已写进 test doc 注释):
1. `rebuild` 在 source 失败时 fail-fast(`populate` 用 `?` 短路),非 graceful 容错。设计取舍:错误透传,不静默丢失。
2. `stats.questions` / `stats.cards` 是**输入计数**(`insert_load_result` 里 +=1),不是 DB 行数。DB 真实行数需 `b.stats()`。

**Regression**:
- `cargo test --workspace` → **112 passed** (109 + 3 新)
- `cargo clippy --workspace -- -D warnings` → 0 errors

## 风险与回滚

- **P0 step 0.1 风险**:若 `CacheStore` 通过 `Arc` 跨线程被多调用方使用,删除 `unsafe impl Sync` 后会编译失败 — 这是**期望行为**,失败暴露问题。
- **P1 step 1.2 风险**:query cap 4096 bytes 可能误伤长 CJK 题干搜索 — 4096 bytes 约 1300 个汉字,题库单题题干几乎不超;足够。
- **P1 step 1.3 风险**:64MB 单文件 cap — 当前 21 banks 总量 16MB(README `cache.db` 16K,题库总题干约数 MB 级),64MB 留 4× 余量。
